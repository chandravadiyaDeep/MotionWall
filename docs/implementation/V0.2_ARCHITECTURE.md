# V0.2 UI and Interactions — Implementation Architecture

## Status and safety

- Target: complete the existing V0.2 Compose UI milestone.
- Base: current `main` branch; all work is isolated on `feature/v0.2-ui-interactions`.
- Do not commit directly to `main`, force-push, or change release signing/versioning.
- Preserve the existing Android Debug APK workflow and website workflow.
- No wallpaper service, video playback, network access, permissions, downloads, or persistent database work in V0.2.

## Verified baseline

- Native Android app: Kotlin, Jetpack Compose, Material 3.
- Single app entry point currently renders the Home/Explore/Favorites/Settings tabs in one `MainActivity.kt`.
- Current sample data is four original gradient placeholders.
- Search and category filtering work; favorite state is in-memory.
- Card tap has no detail destination; Settings is placeholder content.
- Android min SDK 26, compile/target SDK 35, JDK 17, Compose BOM 2024.12.01.
- Existing CI runs `gradle assembleDebug testDebugUnitTest`, uploads the APK, and publishes prereleases on non-PR events.

## V0.2 target architecture

Keep a small, understandable single-module architecture. Do not introduce a multi-module Gradle project or a navigation dependency for this milestone.

```
com.motionwall.app/
  MainActivity.kt                 # Activity + app theme entry
  data/
    SampleWallpapers.kt           # Original local placeholder catalog
  model/
    Wallpaper.kt                  # Immutable wallpaper model
  ui/
    MotionWallApp.kt              # App state, navigation, scaffold
    components/
      WallpaperCard.kt            # Reusable card and favorite affordance
      CategoryChip.kt             # Reusable category filter
      FeaturedMotionCard.kt       # Home hero component
      SectionHeading.kt
    screens/
      HomeScreen.kt
      ExploreScreen.kt
      FavoritesScreen.kt
      SettingsScreen.kt
      WallpaperDetailScreen.kt
    theme/
      MotionWallTheme.kt
```

The exact package/file split may be simplified if a small implementation makes the code clearer, but responsibilities must remain separated.

## State and navigation

- A single app-level state holder owns selected destination, selected wallpaper ID, selected category, search query, favorites, and settings values.
- Use immutable state updates and Compose state APIs; do not hide mutable global state.
- Four top-level destinations: Home, Explore, Favorites, Settings.
- Wallpaper detail is a secondary destination with a visible back action and Android system back support.
- Top-level tab changes clear the detail destination to avoid stale back stacks.
- Search/category filters apply to the catalog; Favorites displays only favorited items.
- V0.2 favorites are session-scoped and survive recomposition, not process death. Persistence is explicitly V0.7.
- Settings controls may be local preview preferences only; do not claim to alter Android system wallpaper or device-wide settings.

## Interaction requirements

- Tap wallpaper card to open detail.
- Favorite toggle is independently clickable and does not open detail.
- Detail screen can toggle favorite and return to the originating catalog.
- Search filters title, category, and tags case-insensitively.
- Category chips select one category; selecting All resets category filtering.
- Empty states provide a clear next action (clear search/reset category or explore wallpapers).
- Settings screen clearly labels preview-only controls and V0.2 limitations.
- Touch targets should be at least 48dp; provide content descriptions/semantics for icon-only controls.
- Back navigation works with both visible back control and system back.

## Visual and motion requirements

- Preserve the existing dark-first purple/pink visual identity and gradient placeholder artwork.
- Use reusable spacing, shape, color, and typography tokens rather than scattering arbitrary values.
- Add restrained Compose transitions for top-level content/detail changes and favorite feedback.
- Avoid continuous infinite animation in catalog cards in V0.2; battery-conscious behavior is a requirement.
- Support narrow and wider widths without horizontal overflow. A responsive 2-column catalog is acceptable on phones; wider screens may use additional columns if implemented safely.

## Testing strategy

- Unit tests for catalog filtering and favorite state transformations.
- Compose UI tests for top-level navigation, search, category selection, card-to-detail, favorite toggling, empty state, and back navigation where test infrastructure allows.
- Existing version metadata tests must continue passing.
- CI remains the source of build/test truth. Do not publish a release from a pull-request workflow.
- Physical-device verification is still required before declaring V0.2 complete.

## Out of scope

- WallpaperService / Engine and Android wallpaper chooser.
- Media3 / ExoPlayer or actual video playback.
- Room/DataStore persistence.
- Downloads, permissions, network catalog, user accounts, analytics.
- OpenGL / Canvas interactive live wallpaper rendering.

## Acceptance criteria

V0.2 is complete only when all four top-level destinations are genuinely distinct and usable; detail/back navigation works; search/category/favorites work; accessibility/touch targets and responsive behavior are checked; automated build and tests pass; physical-device test notes and docs are updated.
